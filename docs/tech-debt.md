# Dette technique — registre

Format : chaque dette = décision assumée pour gagner du temps, avec son plan de remboursement.

| # | Dette | Gain | Risque accepté | Remboursement prévu |
|---|---|---|---|---|
| 1 | Billing manuel (Stripe Payment Link + `planStatus` mis à jour à la main) | ~1 semaine de dev évitée au MVP | Ne scale pas au-delà de ~10 clients ; erreur humaine possible | Intégrer Stripe Billing quand > 5 clients payants |
| 2 | Pool de numéros (voix + VMN SMS) provisionné manuellement chez les fournisseurs | Pas d'intégration API de provisioning à écrire | Onboarding limité au rythme manuel (~OK pour pilotes) | API de provisioning quand > 10 comptes/mois |
| 3 | ~~Un seul fournisseur SMS branché~~ — **remboursée le 17/07** : adapter Twilio écrit et testé (`src/lib/messaging/twilio.ts`, `tests/unit/messaging.test.ts`), webhook entrant (`api/hooks/sms`) accepte le format form-urlencoded Twilio signé en plus du JSON générique. Reste non couvert : migration réelle entre fournisseurs (jamais testée en conditions réelles, l'un ou l'autre est utilisé dès le lancement, pas les deux) | — | Dépendance fournisseur simple (pas de bascule à chaud testée) | Si migration future nécessaire, tester le cutover sur un compte pilote avant bascule générale |
| 4 | Pas de portage du numéro du client (renvoi `*61*` uniquement) | Évite le cauchemar réglementaire/opérationnel du portage | Si le client désactive le renvoi, le produit "ne marche plus" silencieusement → mitigé par un check périodique de `forwardVerifiedAt` (v1.1) | Réévaluer si churn attribuable au renvoi |
| 5 | Pas d'auth self-serve : dashboard derrière HTTP Basic (`src/middleware.ts`), onboarding "white-glove" via `scripts/create-account.ts` | ~1,5 semaine (signup, magic link, sessions, wizard) | Un seul couple user/pass partagé par déploiement — acceptable pour 3-10 pilotes accompagnés, pas au-delà | Vraie auth (magic link + sessions) avant toute ouverture self-serve |
| 6 | Le worker tourne via `tsx src/worker.ts` en prod (pas de build compilé dédié) | Évite une 2e chaîne de build | Démarrage un peu plus lent, surcoût CPU négligeable à notre échelle | Compiler avec esbuild si le démarrage/empreinte devient un sujet |
| 7 | Payload webhook SMS entrant normalisé `{from,to,body}` : le mapping exact smsmode sera figé au spike J1 | Permet de coder/tester tout le flux sans compte smsmode | Ajustement de mapping à prévoir au spike (1-2 h) | Figer au spike + test contractuel sur le payload réel |
| 8 | Pas de Content-Security-Policy (les autres en-têtes de sécurité sont posés dans `next.config.ts`) | Évite le chantier nonces pour le JSON-LD et les styles inline de la landing | Surface XSS théorique — mitigée : aucun contenu utilisateur n'est rendu sur les pages publiques | CSP avec nonces avant l'ouverture self-serve (cf. docs/security-compliance.md §5) |
| 9 | Différenciation des 3 plans appliquée à la main : Artisan+ « 3 lignes » = créer 3 comptes en white-glove, aucune limite logicielle ; l'essai Découverte n'expire pas automatiquement | Stripe Checkout livré sans refonte du modèle de données | Un client Pro pourrait demander 3 lignes sans payer Artisan+ (contrôle humain seulement) ; essais à surveiller à la main | Champ `maxLines` + job d'expiration d'essai quand > 10 clients |
| 10 | Rapprochement paiement Stripe → compte par email uniquement (webhook) : un paiement sans compte existant reste orphelin jusqu'à l'onboarding manuel via /ops | Pas de tunnel signup complet à construire avant le premier client | Si l'email Stripe diffère de l'email compte, statut non mis à jour (visible dans les logs `stripe.no_matching_account`) | Flux signup→checkout avec `client_reference_id=accountId` quand l'auth self-serve existera (dette #5) |
